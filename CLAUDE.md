## What this is

`banana-theme` is one of Pano's official themes: a **thin theme on `@panomc/theme-core`**. The engine (auth flows, plugin
runtime, data loading, routes, default views) comes from the `theme-core/` git submodule (repo `PanoMC/sdk`); this repo
carries only identity, tokens and styles, and its own view overrides. It overrides one engine view (`Navbar`: username tooltip on the avatar dropdown).

It is no longer a fork that tracks vanilla by patch-porting: there is no `src/lib/PluginAPI.js` to keep in sync. Shared
behaviour arrives with an engine bump (`git -C theme-core pull && git add theme-core`, then `bun run sync`,
`bun run check`, `bun run build`).

It is a **free** resource (no `"premium": true` in `manifest.json`), so the license check is skipped at run time; the
build scripts are the same as in the other themes.

Stack: Svelte 5 + SvelteKit + Vite + Bun + Bootstrap 5 + svelte-i18n.

## Layout: who owns what

```
manifest.json  theme.config.js       yours: identity, view overrides, settingsSchema
src/styles/tokens.scss  style.scss   yours: design tokens and the theme's own CSS
src/styles/plugins.scss              yours: plugin UI in this theme's style (rules on the plugins' semantic classes)
src/views/                           yours: overridden views (ejected, registered in theme.config.js)
lang-overrides/                      yours: changed i18n keys only
theme-core/                          submodule: the engine and the SDK
src/routes/  src/lib/  lang/  plugin-contracts/   GENERATED by `bun run sync`: never hand-edit
src/hooks.*.js  *.config.js          two-line factory calls into the engine
```

## Commands

```bash
git submodule update --init          # once after clone
bun install
bun run sync                         # regenerate routes / lib / lang, refresh plugin-contracts/
bun run dev                          # Vite on 3000 (backend via VITE_API_URL); `bun run dev:ui` adds `sass --watch`
bun run check                        # theme-core check (add `-- --strict` before packaging)
bun run build:ui && bun run build
```

SCSS is compiled by `build:ui` / `dev:ui`, not by Vite: use `dev:ui` when you touch styles.

## Plugin UI in this theme

- Every plugin view is a named view (`market:ProductCard`). Its default markup is the plugin's own and is drawn in the
  vanilla look; this theme gives it its style in `src/styles/plugins.scss`, on the semantic classes
  (`<ns>-<view>__<part>`) and the `--pano-*` tokens. No plugin view is ejected here.
- Restyle first; eject a plugin view (`bunx @panomc/theme-core eject-view <ns>:<View>`) only when the structure must
  change. An override must keep every plugin slot, hook and the root class of the default.
- An override whose contract no longer matches the plugin falls back to the plugin's default view and the panel warns;
  nothing breaks. Slot ids, hook names and lifecycle event names are engine-owned.
- New data or behaviour is a plugin change (its controllers or API), never theme code.

## Conventions

- Use Svelte 5 runes. Avoid top-level `onDestroy` in views that plugins mount into; prefer
  `$effect(() => () => cleanup())`. i18n via svelte-i18n's `_` store.
- `svelte` stays pinned exactly to the engine's version.
- Releases via **semantic-release** on `dev` (prerelease) and `master`: one-line conventional commits, no hand-bumped
  versions.
- Sibling themes: `vanilla-theme` (the reference, overrides nothing) and `blaze-theme`, `blocky-theme`, `frost-theme`.

## Agent guide

You are in a **Pano theme** (a thin repo on `@panomc/theme-core`).

Read `agent-guide/README.md` first, then **only** the topic file it points to for your task. Decide from the
request and the code; ask only where the guide says a wrong guess is costly. `agent-guide/` is a synced copy: edit it
in `theme-core/agent-guide/` (repo `PanoMC/sdk`) and run `bun scripts/sync-agent-guide.js` there.

The three rules you will break first:

1. Take the cheapest step: tokens and CSS on semantic classes first, `eject-view` only for structure, `<PluginBlock>` to move a piece; new data or behaviour belongs to the plugin, not the theme (`theme-plugin-ui.md`).
2. Overrides are ejected and registered in `theme.config.js` with their contract; keep every slot, hook and root class; a mismatch falls back to the default view (`theme-override-view.md`).
3. `src/routes/`, `src/lib/`, `lang/` and `plugin-contracts/` are generated; pages, renames and the home page are keys of `theme.config.js`. `theme-core check --strict` must pass (`theme-routes-home.md`, `testing.md`).
